Além da \textit{wiki}, foram criados os repositórios "soul-amada-backend"~e "soul-amada-frontend"~para guardar o código do projeto. Todos estes podem ser encontrados no link: \url{https://tools.ages.pucrs.br/soul-amada}.

\subsection{Banco de Dados Utilizado}
Diante dos requisitos simples para a persistência dos dados, optou-se por utilizar um banco relacional. A ideia inicial era tão simples que, em um primeiro momento, foram conceitualizadas apenas duas tabelas, conforme a Figura~\ref{fig:db-concept}.

O intuito era manter o banco de dados simples, apenas com uma tabela para os usuários e outra para as postagens. Os dados adicionais que não precisariam de tabelas, como devocionais e videoaulas, seriam armazenados diretamente no código do \textit{frontend}.

\subsection{Arquitetura Utilizada}
A estrutura arquitetural do projeto é baseada no design de interação entre componentes distintos. Uma parte do sistema atua como requisitante de serviços ou recursos (o \textit{frontend}, ou cliente), enquanto outra é responsável por processar essas solicitações e fornecer as respostas correspondentes (a API, ou servidor).

A API do projeto Soul Amada é executada em um contêiner Docker hospedado em uma instância \ac{ec2} dentro de uma \ac{vpc} privada, com comunicação direta com o banco de dados da aplicação. O \textit{backend} utiliza o Supabase, uma solução escalável e autogerenciada, para armazenar os dados de forma eficiente.

Para o armazenamento de arquivos, um bucket do S3 foi integrado, simplificando o gerenciamento de dados pela API. Além disso, um API Gateway foi configurado para redirecionar chamadas para a instância EC2, garantindo acesso facilitado e organizado aos serviços da aplicação. Essa arquitetura de \textit{cloud} é apresentada na
Figura~\ref{fig:infra-api}.

\begin{figure}[H]
  \centering
  \small
  \caption{Diagrama da arquitetura na nuvem do projeto Soul Amada}
  \includegraphics[width=1\linewidth]{conteudo//3 - ages II//conteudo//figures/infra.png}

O \textit{deploy} da API ocorre automaticamente após um \textit{commit} na \textit{branch} “main” do repositório \textit{backend}. Um \textit{runner} do GitLab é acionado na própria instância EC2, responsável por executar os testes e aplicar as migrações do \textit{Prisma} \ac{orm} no banco de dados do Supabase. Em seguida, o \textit{runner} realiza o \textit{build} da imagem atualizada da API, finaliza o contêiner que estava em execução e inicia outro com a imagem recém-criada.

O \textit{deploy} do \textit{frontend} também utiliza esse \textit{runner} na EC2 para criar a \ac{apk} e a \ac{ipa}. O \textit{runner} envia esses arquivos para uma pasta de versões no S3, onde ficam disponíveis para download. As Figuras~\ref{fig:infra-api-deploy} e~\ref{fig:infra-front-deploy}
ilustram o fluxo de \textit{deploy} do \textit{backend} e do
\textit{frontend}, respectivamente.

\subsection{Tecnologias Utilizadas}

De maneira geral, a principal tecnologia utilizada foi a linguagem TypeScript, adotada tanto no \textit{frontend} quanto no \textit{backend}, com diferentes \textit{frameworks} em cada camada. No \textit{frontend} foi utilizado o React Native, enquanto no \textit{backend} foi utilizado o NestJS. Além disso, o \ac{sgbd} utilizado foi o Supabase, que é um banco de dados PostgreSQL com uma camada de abstração para facilitar o uso. A camada de persistência da API foi implementada com o Prisma ORM, incluindo a execução de migrações do esquema de dados \cite{typescript,react-native,nestjs,supabase,postgresql,prisma}.

Recursos da AWS também foram utilizados, como o EC2, S3 e API Gateway. O EC2 foi utilizado para hospedar a API, o S3 para armazenar arquivos e o API Gateway para redirecionar chamadas para a instância EC2. O Docker e o GitLab CI também integraram o fluxo de disponibilização da aplicação \cite{aws-docs,docker,gitlab-ci}.
