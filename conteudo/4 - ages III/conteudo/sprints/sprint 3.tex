\subsection{Sprint 3}

Esta sprint se destacou por uma luta minha a tentar configurar um \textit{Runner} do GitLab, algo que em tese era necessário para \textit{pipelines} escritas no GitLab. Enquanto montava o ambiente do servidor, avancei para os primeiros testes de deploy do backend e do banco de dados. Nesse ponto, surgiu a dúvida sobre abandonar o Runner, mas logo ficou claro que, para utilizar o GitLab CI de forma completa, o uso do \textit{Runner} era obrigatório.

Com isso, prossegui instalando e configurando o Runner especificamente para habilitar o deploy automático do \textit{backend}. Após alguns ajustes, consegui realizar um deploy parcial do serviço, ainda pendente apenas da automação do merge para a branch master.

Em paralelo, comecei a estruturar o processo de deploy do front-end. A ideia inicial era montar uma automação que seguisse o fluxo “\textit{GitLab merge → webhook → GitHub Action → git fetch + push → Amplify auto deploy}”. Isso porque o serviço escolhido na AWS (Amplify) não conseguiria acionar o deploy automaticamente devido ao fato de o GitLab utilizado pela AGES ser uma instância hospedada internamente (algo que descobrimos muito tarde). Com essa limitação em mente, passei a testar webhooks do GitLab para disparar as ações necessárias no GitHub e, assim, viabilizar o processo de deploy.

Segui tentando integrar e automatizar os deploys tanto do \textit{backend} quanto do \textit{frontend}, mas novamente acabei esbarrando em dificuldades com o \textit{Runner} no \textit{backend} e falta de memória na nossa EC2, exigindo novas rodadas de ajustes e investigação.
